# 1️⃣ 1교시 \| 텍스트 AI와 코딩 활용
## 1. 텍스트 생성(Text Generation)의 업무 활용
생성형 AI의 텍스트 기능은 단순 문장 작성에 한정되지 않는다. 실제 업무에서는 초안 생성, 요약, 재작성, 번역, 정보 추출, 분류, 질의응답, 비교표 작성 등 다양한 작업에 활용된다.
### 활용 판단 기준
- 반복적으로 많은 텍스트를 처리하는가
- 결과를 사람이 비교·검토할 수 있는가
- 원자료가 명확한가
- 결과 형식이 일정한가
- 사실 오류가 발생했을 때 수정 가능한가
### 핵심
AI가 글을 잘 쓰는지보다 업무의 어느 단계에서 시간을 줄이고 품질을 높일 수 있는지를 먼저 본다.
## 2. 요약(Summarization)
요약은 원문의 핵심 내용을 더 짧은 형태로 재구성하는 작업이다.
### 추출 요약(Extractive Summarization)
원문에서 핵심 문장을 선택하는 방식이다. 원문 표현을 유지하기 때문에 문장 왜곡 위험은 상대적으로 낮지만 흐름이 자연스럽지 않을 수 있다.
### 생성 요약(Abstractive Summarization)
원문의 의미를 바탕으로 새로운 문장으로 요약한다. 읽기 쉽지만 원문에 없는 표현이나 해석이 추가될 수 있다.
### 검증 항목
- 핵심 조건이 빠지지 않았는가
- 숫자와 고유명사가 바뀌지 않았는가
- 원문의 불확실성이 확정적 표현으로 바뀌지 않았는가
- 예외와 제한사항이 누락되지 않았는가
## 3. 정보 추출(Information Extraction)
정보 추출은 긴 문서에서 필요한 항목만 구조화해 뽑는 작업이다.
### 계약서 예시
계약기간, 금액, 해지조건, 위약금, 자동연장 여부를 표로 추출할 수 있다.
### 업무 가치
사람이 문서 전체를 처음부터 읽기 전에 중요한 항목을 빠르게 찾아 검토 순서를 정할 수 있다.
### 주의
AI가 항목을 추출하지 않았다고 문서에 해당 내용이 없다고 단정해서는 안 된다. 누락 가능성을 고려해 원문 위치를 확인해야 한다.
## 4. 재작성(Rewriting)
재작성은 같은 핵심 의미를 유지하면서 대상·목적·문체·길이에 맞게 표현을 바꾸는 작업이다.
### 대표 활용
- 전문 문장을 쉬운 표현으로 변경
- 보고서 문장을 발표용으로 변환
- 긴 문장을 짧게 정리
- 공식 문체와 친근한 문체 전환
### 검증 포인트
표현을 바꾸는 과정에서 사실 의미, 책임 범위, 법적 조건이 바뀌지 않았는지 확인한다.
## 5. 문서 기반 질의응답(Document Question Answering)
문서 기반 질의응답은 업로드하거나 지정한 자료를 중심으로 질문하고 답을 받는 방식이다.
### 기본 절차
1. 문서 범위 지정
2. 질문 구체화
3. 답변 생성
4. 근거 위치 확인
5. 원문 대조
### 좋은 질문 예
`이 문서에서 2025년 매출 감소 원인으로 직접 제시한 항목만 표로 정리하고 해당 문단을 함께 표시해줘.`
### 실무 가치
긴 문서를 모두 읽기 전에 탐색 속도를 높일 수 있지만 최종 판단은 반드시 원문 근거를 확인해야 한다.
## 6. 여러 문서 비교
AI는 여러 문서의 공통점과 차이를 빠르게 정리할 수 있다. 그러나 비교 기준을 정하지 않고 `비교해줘`라고 요청하면 중요하지 않은 차이를 강조할 수 있다.
### 비교 기준 예
- 목적
- 대상
- 비용
- 일정
- 장점
- 위험
- 필수 조건
### 실무 원칙
비교 기준을 사람이 먼저 정의하고, AI에게 동일 기준으로 모든 문서를 분석하도록 요청한다.
## 7. 텍스트 결과 검증 5단계
1. 원문에 없는 주장 표시
2. 숫자 대조
3. 고유명사 대조
4. 조건·예외 대조
5. 최신성 확인
### 추가 점검
AI가 내용을 자연스럽게 연결하면서 서로 다른 문서의 주장을 섞지 않았는지도 확인한다.
## 8. 코드 생성(Code Generation)
AI는 자연어 요구사항을 바탕으로 코드 초안을 생성할 수 있다.
### 활용
- 반복 코드 작성
- 데이터 변환
- 함수 초안
- 테스트 코드 생성
- 오류 메시지 설명
### 한계
생성된 코드는 실행 가능성, 성능, 보안, 예외처리를 보장하지 않는다. 코드는 텍스트 결과보다 실행 시 실제 시스템에 영향을 줄 수 있으므로 검증 기준을 더 높게 잡아야 한다.
## 9. 코드 리뷰(Code Review)
AI에게 기존 코드의 구조와 문제점을 검토하게 할 수 있다.
### 검토 항목
- 논리 오류
- 예외 처리
- 입력 검증
- 보안 위험
- 성능
- 가독성
- 중복 코드
### 활용 방식
AI 제안을 그대로 반영하지 않고 개발자가 실제 요구사항과 실행환경을 기준으로 검토한다.
## 10. 테스트(Test)와 검증
AI가 코드를 만들었더라도 사람이 테스트 케이스(Test Case)를 설계해야 한다.
### 기본 테스트
- 정상 입력
- 빈 입력
- 최대·최소값
- 잘못된 형식
- 예상하지 못한 입력
- 권한이 없는 사용자 입력
### 핵심
AI가 만든 코드는 완성품이 아니라 검토가 필요한 초안으로 취급한다.
---
### 심화 해설 \| 요약 목적에 따라 결과 구조를 바꾼다
같은 원문도 누구를 위해 요약하는지에 따라 결과가 달라진다. 경영진 보고용 요약은 의사결정 포인트와 위험을 강조하고, 실무자용 요약은 조건·일정·담당 업무를 구체적으로 남겨야 한다. 따라서 `요약해줘`보다 독자, 사용 목적, 반드시 유지할 정보를 함께 지정한다.
### 심화 해설 \| 정보 추출과 해석을 분리한다
문서에서 금액, 날짜, 조건을 뽑는 작업과 그 의미를 판단하는 작업은 구분해야 한다. 추출 단계에서는 원문에 있는 사실을 그대로 구조화하고, 해석 단계에서는 위험이나 중요도를 평가한다. 두 단계를 섞으면 모델이 원문에 없는 판단을 사실처럼 표시할 수 있다.
### 심화 해설 \| 다중 문서 비교에서 기준표를 만든다
여러 제안서나 정책 문서를 비교할 때는 문서별로 다른 표현을 그대로 나열하기보다 동일한 비교 기준을 먼저 정의한다. `비용 / 일정 / 필수조건 / 위험 / 기대효과 / 근거 위치`처럼 기준표를 만들면 문서 간 차이를 일관되게 볼 수 있다.
### 심화 해설 \| 코드 생성은 요구사항 명세부터 시작한다
코드 품질은 프롬프트 문장보다 요구사항의 명확성에 크게 좌우된다. 입력 형식, 예상 출력, 오류 처리, 성능 조건, 실행 환경, 금지 라이브러리 등을 명확히 제시하면 검증 가능한 코드가 나온다.
### 심화 해설 \| 테스트 주도 검증(Test-Driven Validation)
AI에게 코드를 생성하게 할 때 먼저 테스트 조건을 정의하면 결과를 객관적으로 검증하기 쉽다. 정상 입력뿐 아니라 빈 값, 잘못된 형식, 경계값, 예외 상황을 포함한 테스트 케이스를 준비한다.
# 2️⃣ 2교시 \| PPT·자동화·통합 업무 제작
## 1. 프레젠테이션(Presentation)의 목적
좋은 PPT는 많은 내용을 담는 문서가 아니라 발표자가 전달할 메시지를 시각적으로 구조화한 도구다.
### 먼저 결정할 것
- 발표 목적
- 청중
- 발표 시간
- 핵심 메시지
- 청중이 기억해야 할 결론
### 실무 원칙
PPT 도구를 먼저 선택하기보다 전체 논리 흐름과 슬라이드별 메시지를 먼저 설계한다.
## 2. 정보 압축(Information Compression)
긴 문서를 슬라이드로 바꿀 때 모든 문장을 조금씩 줄이는 방식은 좋은 압축이 아니다. 핵심 주장과 이를 뒷받침하는 근거를 분리하고, 발표에 필요하지 않은 세부 정보를 덜어내야 한다.
### 슬라이드 기본 구조
- 핵심 메시지 1개
- 핵심 근거 2\~4개
- 필요한 시각 자료
- 출처 또는 근거
### 판단 포인트
슬라이드를 보지 않고 제목만 읽어도 발표의 논리 흐름이 이해되는지 확인한다.
## 3. 슬라이드 아웃라인(Slide Outline)
PPT를 바로 만들기 전에 슬라이드 순서를 설계한다.
### AI 도입 제안 예
1. 현재 문제
2. 업무 현황
3. AI 적용 후보
4. 기대 효과
5. 위험과 한계
6. 실행 계획
7. 비용
8. 결론
### 장점
디자인에 시간을 쓰기 전에 논리의 누락과 중복을 발견할 수 있다.
## 4. 결론형 슬라이드 제목
`시장 현황`처럼 주제만 쓰는 제목보다 `AI 교육 시장은 대학·기업 교육을 중심으로 확대되고 있다`처럼 핵심 메시지가 드러나는 제목이 이해를 돕는다.
### 좋은 제목의 조건
- 한 문장으로 메시지가 드러남
- 본문 근거와 일치함
- 과장된 단정이 없음
- 발표 흐름과 연결됨
## 5. AI로 PPT를 만들 때 발생하는 대표 문제
- 한 슬라이드에 너무 많은 문장
- 반복되는 일반론
- 근거 없는 숫자
- 장식적 이미지 과다
- 출처 누락
- 발표 흐름보다 템플릿 중심 구성
### 대응 원칙
AI가 만든 슬라이드 초안도 문서 요약과 동일하게 원자료, 숫자, 출처, 메시지의 우선순위를 사람이 검토한다.
## 6. AI 자동화(AI Automation)
AI 자동화는 생성형 AI를 반복 업무 프로세스에 연결해 입력을 받고 처리한 뒤 다음 단계로 전달하는 구조다.
### 예시
고객 문의 수신 → 문의 유형 분류 → 핵심 내용 요약 → 담당 부서 지정 → 답변 초안 생성 → 사람 검토 → 발송
### 중요한 점
AI 자동화는 ‘AI가 모든 일을 자동으로 한다’는 의미가 아니다. 반복 처리와 사람 판단 단계를 적절히 연결하는 업무 설계다.
## 7. 자동화 후보 업무의 조건
자동화에 적합한 업무는 반복 빈도가 높고 입력 구조가 일정하며 판단 기준이 비교적 명확한 경우가 많다.
### 적합한 업무
- 반복 분류
- 정형화된 요약
- 일정한 양식의 초안
- 데이터 필드 추출
### 주의가 필요한 업무
- 예외가 매우 많음
- 법적 책임이 큼
- 사람의 공감과 협상이 핵심
- 오류가 즉시 큰 피해로 이어짐
## 8. 트리거(Trigger)와 액션(Action)
자동화는 특정 사건을 시작점으로 동작한다.
### 트리거
이메일 수신, 새 파일 업로드, 폼 제출, 특정 시간 도달 등이 있다.
### 액션
내용 요약, 데이터 저장, 메시지 발송, 문서 생성, 담당자 알림 등이 있다.
### 실무 포인트
트리거와 액션 사이에 조건 검증 없이 자동 실행되면 잘못된 입력이 다음 단계로 빠르게 확산될 수 있다.
## 9. 조건 분기(Conditional Branching)
조건 분기는 입력 내용에 따라 다른 작업 흐름을 선택하도록 만드는 구조다.
### 예
- 긴급도 높음 → 담당자 즉시 알림
- 일반 문의 → 답변 초안 생성
- 개인정보 포함 → 자동 처리 중단 후 사람 검토
### 중요성
모든 입력을 같은 흐름으로 처리하지 않고 위험 수준과 예외를 업무 규칙으로 반영할 수 있다.
## 10. 사람 승인(Human Approval)
중요한 결과를 자동으로 실행하기 전에 사람이 확인하도록 하는 단계다.
### 반드시 고려할 상황
- 외부 이메일 발송
- 결제·환불
- 개인정보 처리
- 계약 관련 문서
- 공개 게시물
### 승인 단계의 조건
담당자가 결과를 실제로 읽고 수정·거절할 수 있어야 하며 단순 클릭 절차가 되어서는 안 된다.
## 11. 예외 처리(Exception Handling)와 실패 대비
자동화는 정상 흐름뿐 아니라 실패 흐름도 설계해야 한다.
### 대표 예외
- 입력이 비어 있음
- AI 응답 실패
- 분류 신뢰도가 낮음
- 외부 시스템 연결 실패
- 중복 실행
### 대응
재시도, 사람에게 전달, 오류 로그 기록, 작업 중단, 관리자 알림 등의 방식을 설계한다.

하나의 업무 상황을 선택해 텍스트 AI, 코드 또는 데이터 처리, PPT, 자동화 흐름을 연결한다.

## ### 심화 해설 \| 슬라이드 한 장에는 하나의 메시지를 둔다
PPT가 문서처럼 장문의 내용을 담으면 발표자의 설명과 화면 정보가 경쟁한다. 슬라이드마다 핵심 결론 하나를 두고 근거와 시각 자료는 그 결론을 지원하도록 배치한다. 상세 내용은 발표자 노트나 부록으로 분리할 수 있다.
### 심화 해설 \| 차트와 이미지도 근거가 필요하다
AI가 만든 PPT는 그럴듯한 차트나 아이콘을 자동으로 넣을 수 있지만 실제 데이터와 연결되지 않은 시각 자료가 포함될 수 있다. 수치 차트는 원자료와 계산 근거를 확인하고, 설명용 이미지는 사실성을 검토한다.
### 심화 해설 \| 자동화의 트리거(Trigger)와 액션(Action)
자동화는 무엇이 작업을 시작하게 하는지와 이후 어떤 행동을 수행하는지를 구분한다. 이메일 수신, 폼 제출, 특정 시간 도달이 트리거가 될 수 있고, 요약·분류·문서생성·알림이 액션이 될 수 있다.
### 심화 해설 \| 조건 분기(Conditional Branching)
모든 입력을 같은 방식으로 처리하면 예외 상황에 취약하다. 긴급 문의, 개인정보 포함 문의, 신뢰도가 낮은 분류 결과처럼 조건에 따라 사람에게 넘기거나 다른 절차로 분기하도록 설계한다.
### 심화 해설 \| 실패 흐름(Failure Path)을 설계한다
자동화는 정상 흐름뿐 아니라 AI 응답 실패, 외부 시스템 연결 오류, 중복 실행, 입력 누락 상황을 고려해야 한다. 재시도, 작업 중단, 사람 전달, 오류 로그 기록 같은 대응을 사전에 정의한다.
### 심화 해설 \| 자동화 성과를 측정한다
자동화 성공 여부는 실행 횟수가 아니라 처리시간 감소, 재작업률, 오류율, 사람 검토시간, 고객 응답속도 등 실제 업무 지표로 평가한다. 자동화가 늘었지만 검토 부담이 더 커졌다면 개선이 필요한 구조다.
## 🔎 핵심 정리
- 텍스트 AI는 요약·정보 추출·재작성·문서 질의응답에 유용하지만 숫자·고유명사·조건을 원문과 검증해야 한다.
- AI가 만든 코드는 실행 가능한 초안일 뿐이므로 테스트·보안·예외처리를 사람이 확인해야 한다.
- 좋은 PPT는 장식보다 핵심 메시지와 정보 계층을 먼저 설계하며 슬라이드 제목 자체가 결론을 전달해야 한다.
- AI 자동화는 트리거·액션·조건 분기·사람 승인·예외 처리까지 포함한 전체 업무 워크플로로 설계해야 한다.
## 🔎 추가 심화 학습 \| 텍스트 업무를 유형별로 분리하기
텍스트 AI를 잘 활용하려면 모든 문서 업무를 ‘글쓰기’로 묶지 않고 목적에 따라 나누어야 한다. 요약, 추출, 분류, 재작성, 질의응답, 비교, 초안 작성은 서로 다른 검증 기준을 가진다.
### 분류(Classification)
문서를 정해진 범주로 나누는 작업이다. 고객 문의 유형, 위험 등급, 문서 종류 분류 등에 활용할 수 있다. 분류 기준과 예외 범주를 명확히 정의해야 한다.
### 정보 추출과 요약의 차이
정보 추출은 원문에 있는 값을 그대로 구조화하는 데 초점이 있고, 요약은 내용을 압축해 재구성하는 작업이다. 계약 금액을 뽑는 것은 추출이고 계약의 핵심 쟁점을 정리하는 것은 요약이다.
### 비교(Comparison)
여러 문서를 같은 기준으로 비교하는 작업이다. 비교 기준이 없으면 AI가 임의로 중요도를 정할 수 있으므로 사람이 먼저 항목을 정의한다.
### 초안 생성(Drafting)
기획된 구조에 맞춰 새로운 문장을 만드는 작업이다. 초안은 검토가 필요한 중간 산출물로 취급하고 원자료와 요구사항을 대조한다.
## 🔎 추가 심화 학습 \| 코드 활용을 안전하게 만드는 기준
### 실행 환경(Runtime Environment)
같은 코드도 운영체제, 라이브러리 버전, 데이터 형식에 따라 다르게 동작할 수 있다. 코드 생성 요청에는 실행 환경을 명시하는 것이 좋다.
### 의존성(Dependency)
외부 라이브러리와 패키지는 편리하지만 보안 취약점과 버전 충돌 위험이 있다. 생성된 코드가 불필요한 의존성을 추가하지 않는지 확인한다.
### 입력 검증(Input Validation)
사용자 입력을 그대로 실행하거나 데이터베이스 쿼리에 전달하면 보안 문제가 발생할 수 있다. 형식, 길이, 허용값을 검증하고 예외를 처리해야 한다.
### 오류 처리(Error Handling)
정상 상황만 고려한 코드는 실제 서비스에서 쉽게 실패한다. 파일 없음, 네트워크 오류, 빈 데이터, 권한 부족 등 예상 가능한 오류를 어떻게 처리할지 설계한다.
### 코드 설명과 코드 검증은 다르다
AI가 자신이 만든 코드를 자연스럽게 설명한다고 해서 코드가 정확하다는 뜻은 아니다. 실제 실행, 테스트, 리뷰가 필요하다.
## 🔎 추가 심화 학습 \| PPT 제작을 메시지 구조로 보기
### 슬라이드 한 장의 역할
슬라이드마다 하나의 핵심 질문에 답하도록 설계한다. `시장 현황`, `문제점` 같은 제목보다 결론이 드러나는 제목을 사용하면 발표 흐름을 이해하기 쉽다.
### 근거와 주장 분리
슬라이드의 제목은 주장이고 차트·수치·인용은 근거 역할을 한다. 근거가 제목의 결론을 실제로 뒷받침하는지 확인해야 한다.
### 정보 밀도(Information Density)
한 슬라이드에 너무 많은 내용을 넣으면 발표자가 읽는 문서가 된다. 핵심 메시지, 필수 근거, 시각 자료를 남기고 상세 설명은 발표자 노트나 부록으로 분리한다.
### 부록(Appendix)
본문 흐름을 방해하지만 질의응답에 필요한 상세 데이터나 방법론은 부록으로 분리할 수 있다. AI에게도 본문과 부록의 역할을 구분해 생성하도록 요청한다.
## 🔎 추가 심화 학습 \| AI 자동화 설계
### 트리거(Trigger)
자동화가 시작되는 조건이다. 이메일 수신, 폼 제출, 파일 업로드, 일정 도래 등이 될 수 있다.
### 액션(Action)
트리거 이후 수행하는 작업이다. 분류, 요약, 데이터 저장, 알림 발송 등이 있다.
### 조건 분기(Conditional Branch)
모든 입력을 같은 방식으로 처리하지 않고 조건에 따라 경로를 나눈다. 예를 들어 긴급 문의는 즉시 담당자에게 보내고 일반 문의만 AI가 초안을 만들게 할 수 있다.
### 사람 승인(Human Approval)
외부 발송, 비용 발생, 고객에게 영향을 주는 행동은 자동 실행 전에 사람이 확인하도록 설계한다.
### 재시도(Retry)와 실패 처리
외부 시스템 오류나 일시적인 실패가 있을 수 있으므로 재시도 횟수와 실패 시 알림 규칙을 정한다. 무한 재시도는 중복 처리와 비용 증가를 만들 수 있다.
### 관찰 가능성(Observability)
자동화가 정상적으로 작동하는지 알기 위해 처리 건수, 실패율, 지연시간, 사람 수정률을 기록한다.

## 📌 학습 요약
- 텍스트 생성(Text Generation)은 요약(Summarization)·정보 추출(Information Extraction)·재작성(Rewriting)·문서 기반 질의응답(Document Question Answering)처럼 목적에 따라 작업 유형을 구분해야 한다.
- AI가 만든 텍스트는 원문에 없는 주장, 숫자·고유명사 오류, 조건 누락이 없는지 원자료와 대조해야 하며 추출과 해석 단계를 분리하면 오류를 줄일 수 있다.
- 코드 생성(Code Generation)과 코드 리뷰(Code Review)는 요구사항·실행환경·예외 처리·테스트 케이스(Test Case)를 명확히 정의하고 실제 실행 검증을 거쳐야 한다.
- 프레젠테이션(Presentation)과 AI 자동화(AI Automation)는 정보 압축·슬라이드 메시지·업무 흐름·사람 승인(Human Approval)을 함께 설계해야 실무 생산성과 안정성을 높일 수 있다.
